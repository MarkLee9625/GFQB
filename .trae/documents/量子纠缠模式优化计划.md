# 量子纠缠模式优化计划

## 📋 问题分析

### 当前架构痛点

目前项目的"量子纠缠模式"（编辑版和阅读版）存在以下核心问题：

1. **代码重复严重**：
   - 编辑器组件（`Editor.tsx`）和阅读版（`reader.ts` + `templates.ts`）各自维护一套 UI 渲染逻辑
   - 封面/封底设计在两个地方都有实现（Editor 中的预览 + PaperView + 阅读版模板）
   - 样式系统在编辑器和阅读版之间不同步（如 `SHARED_STYLES`、`MAGAZINE_STYLES` 等）

2. **UI 变更成本高**：
   - 每次新增功能或修改样式时，需要在多个文件中重复修改：
     - `components/Editor.tsx` - 编辑器预览
     - `components/PaperView.tsx` - 编辑器阅读视图
     - `src/services/export/templates.ts` - 阅读版模板
     - `src/services/export/reader.ts` - 数据导出逻辑
   - 容易遗漏导致显示不一致

3. **数据流割裂**：
   - 编辑器使用 React 状态管理
   - 阅读版使用纯 JS 模板渲染
   - 两者之间没有共享的组件或渲染引擎

4. **知识图谱渲染复杂**：
   - `graphRenderer.ts` 需要同时处理编辑版和阅读版的渲染
   - 使用 iframe 隔离，通信复杂
   - 打印版和屏幕版需要分别处理

## 🔍 同类开源项目参考

### 1. **Notion** (文档编辑器)
- **架构特点**：单一数据源 + 多视图渲染
- **核心机制**：
  - 使用 Block 数据结构统一存储内容
  - 编辑器、阅读版、打印版共享同一套渲染引擎
  - 通过 Props 控制不同模式下的行为（可编辑 vs 只读）
- **借鉴点**：
  - 提取统一的 `ArticleRenderer` 组件
  - 通过 `mode` 属性区分编辑/阅读/打印模式

### 2. **MDX Editor** (Markdown 编辑器)
- **架构特点**：插件化架构 + 实时预览
- **核心机制**：
  - 编辑器核心与预览组件共享同一套 AST 解析器
  - 预览组件是编辑器的"只读快照"
  - 使用 React Context 同步状态
- **借鉴点**：
  - 将 PaperView 改造为 Editor 的子组件
  - 使用 Context 或 Props 传递数据，而非重新渲染

### 3. **Craft.js** (页面构建器)
- **架构特点**：组件序列化 + 渲染器分离
- **核心机制**：
  - 将页面结构序列化为 JSON
  - 提供 `Editor` 和 `Frame` 两个组件共享渲染逻辑
  - 通过 `renderComponent` 配置控制渲染行为
- **借鉴点**：
  - 将文章结构序列化为标准 JSON Schema
  - 编辑器和阅读版都从 JSON Schema 渲染

### 4. **Gutenberg** (WordPress 编辑器)
- **架构特点**：Block 编辑器 + 前后端分离
- **核心机制**：
  - 前端编辑器使用 React 组件
  - 后端存储为标准 HTML + 元数据
  - 阅读版直接渲染 HTML，共享 CSS 样式系统
- **借鉴点**：
  - 统一 CSS 样式系统（编辑器预览 = 阅读版样式）
  - 使用 `contentEditable` + 标准 HTML 输出

## 🎯 优化方案

### **方案 A：单一渲染引擎架构**（推荐）

#### 核心思想
将 PaperView 改造为可复用的渲染组件，通过 Props 控制行为模式：

```typescript
interface ArticleRendererProps {
  article: Article;
  mode: 'edit' | 'read' | 'print';
  isEditable?: boolean;
  onUpdate?: (updates: Partial<Article>) => void;
  logo?: string;
}

const ArticleRenderer: React.FC<ArticleRendererProps> = ({
  article,
  mode,
  isEditable = false,
  onUpdate,
  logo
}) => {
  // 共享的渲染逻辑
  const renderContent = () => {
    // 统一的 HTML 渲染
  };
  
  const renderCover = () => {
    // 统一的封面渲染（支持编辑模式）
  };
  
  // 根据 mode 应用不同的样式类
  return (
    <div className={`article-renderer mode-${mode} ${isEditable ? 'editable' : ''}`}>
      {/* 共享的渲染逻辑 */}
    </div>
  );
};
```

#### 实施步骤

**Phase 1: 提取共享渲染组件**（优先级：高）
1. 创建 `components/ArticleRenderer.tsx`
2. 将 PaperView 的逻辑迁移到 ArticleRenderer
3. 支持 `mode` 属性控制行为：
   - `edit`: 启用编辑功能（拖拽、缩放、内容编辑）
   - `read`: 只读模式，优化交互
   - `print`: 应用打印样式

**Phase 2: 重构 Editor 组件**（优先级：高）
1. 移除 Editor 中的封面/封底预览逻辑
2. 使用 ArticleRenderer 替代现有的预览
3. 通过 Props 传递 `isEditable=true` 和 `onUpdate` 回调

**Phase 3: 重构阅读版导出**（优先级：中）
1. 将 `templates.ts` 中的模板改为使用 ArticleRenderer
2. 阅读版 SSR 渲染时，直接调用 ArticleRenderer 生成 HTML
3. 共享同一套样式系统（`SHARED_STYLES`）

**Phase 4: 统一样式系统**（优先级：中）
1. 创建 `styles/article-renderer.css`
2. 将编辑器预览、PaperView、阅读版的样式统一
3. 使用 CSS 变量控制主题（如字体大小、行距等）

**Phase 5: 知识图谱渲染优化**（优先级：低）
1. 将 graphRenderer 改造为 React 组件
2. 支持在编辑器和阅读版中共享
3. 打印版使用静态 SVG，屏幕版使用 Canvas

#### 优势
- ✅ **单一数据源**：所有视图从同一套组件渲染
- ✅ **样式一致**：编辑器预览 = 阅读版效果
- ✅ **维护成本低**：修改一处，全局生效
- ✅ **类型安全**：使用 TypeScript 统一接口定义

#### 劣势
- ⚠️ 重构工作量大，需要改动核心架构
- ⚠️ 需要确保阅读版的性能不受影响

### **方案 B：代码生成架构**（保守方案）

#### 核心思想
保持现有架构不变，通过代码生成工具自动同步修改：

1. 创建 `scripts/sync-templates.ts` 脚本
2. 定义 UI 变更的"单一事实源"（如 Editor 组件）
3. 构建时自动将 Editor 的 UI 结构同步到阅读版模板

#### 实施步骤

**Phase 1: 建立同步机制**
1. 分析 Editor 和 PaperView 的 DOM 结构差异
2. 创建映射规则，将 React JSX 转换为阅读版模板字符串
3. 在 `post-build.js` 中集成同步逻辑

**Phase 2: 样式同步**
1. 将 Tailwind 类名映射为阅读版的 CSS 类名
2. 创建样式映射表（`tailwind-to-css-map.json`）
3. 构建时自动转换样式

**Phase 3: 数据流同步**
1. 确保 Editor 和 PaperView 使用相同的 Article 数据结构
2. 在导出时，直接复用 Editor 的渲染结果

#### 优势
- ✅ 改动较小，风险低
- ✅ 保持现有架构稳定

#### 劣势
- ⚠️ 代码生成逻辑复杂，维护成本高
- ⚠️ 无法完全解决样式不一致问题
- ⚠️ 调试困难

### **方案 C：混合架构**（折中方案）

#### 核心思想
结合方案 A 和 B：
1. 将核心渲染逻辑提取为共享组件（ArticleRenderer）
2. 阅读版模板使用代码生成工具从共享组件生成
3. 编辑器直接使用共享组件

#### 实施步骤

**Phase 1: 提取共享组件**（同方案 A）

**Phase 2: 构建时渲染**
1. 在 `post-build.js` 中，使用 React SSR 渲染 ArticleRenderer
2. 将渲染结果注入阅读版模板
3. 样式系统自动内联

**Phase 3: 增量迁移**
1. 优先迁移封面/封底组件
2. 逐步迁移正文渲染逻辑
3. 最终完全替换旧模板

#### 优势
- ✅ 渐进式重构，风险可控
- ✅ 最终实现单一渲染引擎
- ✅ 阅读版保持纯静态，性能优秀

#### 劣势
- ⚠️ 需要维护 SSR 渲染逻辑
- ⚠️ 构建时间可能增加

## 📝 代码示例

### ArticleRenderer 组件结构

```typescript
// components/renderers/ArticleRenderer.tsx
import React, { useState, useCallback } from 'react';
import { Article } from '../types';
import { CoverRenderer } from './CoverRenderer';
import { BackRenderer } from './BackRenderer';
import { ContentRenderer } from './ContentRenderer';

interface ArticleRendererProps {
  article: Article;
  mode: 'edit' | 'read' | 'print';
  logo?: string;
  onArticleUpdate?: (id: number, updates: Partial<Article>) => void;
  onImageUpload?: (type: 'cover' | 'back') => void;
  onNext?: () => void;
  useAlternateDesign?: boolean;
}

export const ArticleRenderer: React.FC<ArticleRendererProps> = ({
  article,
  mode,
  logo,
  onArticleUpdate,
  onImageUpload,
  onNext,
  useAlternateDesign = false
}) => {
  const isEditable = mode === 'edit';
  
  // 渲染封面
  const renderCover = () => (
    <CoverRenderer
      article={article}
      isEditable={isEditable}
      onImageUpload={onImageUpload}
      onUpdate={onArticleUpdate}
      onNext={onNext}
      useAlternateDesign={useAlternateDesign}
    />
  );
  
  // 渲染封底
  const renderBack = () => (
    <BackRenderer
      article={article}
      isEditable={isEditable}
      onImageUpload={onImageUpload}
      onUpdate={onArticleUpdate}
      useAlternateDesign={useAlternateDesign}
    />
  );
  
  // 渲染正文
  const renderContent = () => (
    <ContentRenderer
      article={article}
      isEditable={isEditable}
      logo={logo}
    />
  );
  
  // 根据文章类型选择渲染内容
  if (article.category === '封面') {
    return renderCover();
  }
  
  if (article.category === '封底') {
    return renderBack();
  }
  
  return renderContent();
};
```

## ⚠️ 注意事项

1. **性能优化**：
   - 阅读版必须保持纯静态，不能有客户端 JavaScript 执行
   - SSR 渲染时要注意内存泄漏问题
   - 图片懒加载机制需要保留

2. **样式隔离**：
   - 确保阅读版的样式不会影响编辑器
   - 使用 CSS 模块或 BEM 命名规范

3. **向后兼容**：
   - 保留旧版阅读器的导出格式
   - 提供迁移工具或兼容性层

4. **测试覆盖**：
   - 每个 Phase 完成后都要进行完整的回归测试
   - 重点测试封面/封底的拖拽、缩放功能
   - 测试打印版式的兼容性
