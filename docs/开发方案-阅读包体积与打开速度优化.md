# 开发方案：阅读包体积与打开速度优化

> 编制日期：2026-10-20 ｜ 状态：**待开发**（本文档为后续开发依据，编制时未改动任何生产代码）
> 关联文档：`开发方案-性能优化与功能增强.md`（编辑器侧 P0–P3）。本文专注**导出的单文件电子阅读包**，与之互补、编号独立（R 系列）。

---

## 0. 背景与目标

生产的交互阅读版（单 HTML 离线阅读包）体积达 **200~260MB**，且打开迟缓、内存占用高。用户诉求两条：

1. **必须保持单文件**（单个 `.html` 自包含分发）——这是硬约束，排除"媒体外置"路线；
2. **提升打开速度**（电子阅读版）。

本方案在单文件约束内，同时打**减体积**与**提打开速度**两个目标。**两条主线共用同一个根因**（数据层全量 eager 解析），因此 T 系列（提速）与 S 系列（减体积）应协同设计。

**目标量化**：
- 打开首屏：从"等全量 JSON 解析完（数秒~十几秒）"→ **秒开**（先出封面/目录）；
- 内存峰值：从 GB 级 → **几十 MB**；
- 包体积：在 gzip 生效前提下，从 ~150MB → **<60MB**；若历史产物为未压缩（见 §1 校准），则修复后从 259MB 直接落到该量级。

## 1. 现状实测证据

### 1.1 体积账目（实测 `2026第1期/SWS_工法情报_阅读版.html`，27 篇 / 70 处媒体）

| 阶段 | 体积 | 相对原始 |
|---|---|---|
| 真实媒体二进制（图片+视频原始字节） | **145.4 MB** | 1.00× |
| 第 1 次 base64（媒体塞进 JSON 字符串） | 193.9 MB | ×1.33 |
| 第 2 次 base64（整个 JSON 再编码进 HTML） | 260 MB | ×1.77 |

**干货构成（145.4MB）**：

| 媒体 | 真实二进制 | 占比 | gzip 能否压 |
|---|---|---|---|
| 视频 mp4 | 80.8 MB | 55% | ❌ 已压缩 |
| 图片 PNG | 58.8 MB | 40% | ❌ 已压缩（**且不该这么大，见 S2**） |
| 图片 JPEG | 5.7 MB | 4% | ❌ 已压缩 |
| 图片 GIF | 0.2 MB | <1% | ❌ |

单篇极端值：`[视频]韩华海洋焊接机器人…` **65.75MB**、`【视频】探索自动化…` 30.64MB —— 两篇视频占 96MB。

### 1.2 ⚠️ 关键校准：历史产物疑似未走 gzip（**先测后改的依据**）

实测该 259MB 文件：
- `__SWS_COMPRESSION_METHOD__` 标记**不存在**；
- 数据段 base64 解码后**直接是明文 JSON**（首字符 `[{`），**不是 gzip**。

但**当前代码** [reader.worker.ts:52](../src/services/export/reader.worker.ts) 明确调用 `compressData(rawArticlesJson, 'gzip')`，[reader.ts:111](../src/services/export/reader/reader.ts) 与 [readerSkeleton.ts:44](../src/services/export/reader/readerSkeleton.ts) 都写入 `__SWS_COMPRESSION_METHOD__`。

**推断**：这些历史阅读包是**旧版代码导出**的（在 worker gzip 链路引入之前，或走了 dev 回退骨架 `buildReaderHTML`）。

**为什么必须先测**：
- gzip 对"base64 文本"有效（能找回 base64 的 33% 膨胀）。若新导出确实走 gzip，那么"双重 base64"的膨胀**已被 gzip 吃掉大半**，S1（去双重 base64）收益从 25% 缩到很小；
- 真正救不了的是 **PNG / MP4 这类已压缩媒体**（gzip 无效），它们才是 gzip 生效后的硬体积大头；
- **结论：改造前必须用当前代码重新导出一份测基线**（R0），否则会照着旧文件的病去改新代码、收益错配。

### 1.3 打开慢的完整链条

| 环节 | 现状 | 问题 |
|---|---|---|
| 读盘 | 260MB 在 **OneDrive 目录** | 若"按需文件"，打开前先**下载 260MB**（环境主因） |
| HTML 解析 | 260MB 文本进 DOM | JS 字符串 UTF-16 ≈ **520MB 内存** |
| 解码 | `atob`→`escape`→`decodeURIComponent`（[boot.ts:76-78](../src/services/export/reader/client/boot.ts)） | ⚠️ 逐字符老式解码 260MB，**极慢**（仅 `method==='none'` 走此路径） |
| JSON.parse | **全量解析 194MB / 27 篇** | ⚠️ 哪怕只看封面也等全部解析完，卡 UI、内存峰值高 |
| 渲染 | 已懒加载（`IntersectionObserver` + `video preload="metadata"` + `requestIdleCallback`） | ✅ 这层已做好 |

**核心矛盾**：渲染层是懒的，**数据层是全量 eager 的** —— 打开即把 27 篇含 80MB 视频的 JSON 一次性吃进内存。这是"慢"与"内存大"的**共同根源**（T2 根治点）。

## 3. R0 基线验证（先测后改，零代码改动）

### 目标
用**当前代码**重新导出一份阅读包，测出真实画像，作为后续改造的对照基线。

### 实施步骤
1. `npm run build` 后，用当前编辑器导出一份含**视频 + PNG + JPEG** 的阅读包（复现 `2026第1期` 那种内容）。
2. 测量并记录（脚本可复用 `_体积分析/analyze2.py`）：
   - 包体积、`__SWS_COMPRESSION_METHOD__` 值（`gzip` 还是 `none`）；
   - 数据段解码后是 gzip 还是明文 JSON；
   - 各媒体 mime 的真实二进制占比（重点看 PNG 是否仍异常大）；
   - 打开耗时（Performance 面板：`atob`/解码/`JSON.parse` 各环节）与内存峰值。
3. 对比历史产物（259MB），确定：
   - gzip 是否生效（决定 S1/S3 收益）；
   - PNG 大户的具体来源（哪篇文章/哪个字段，见 R2）。

### 验收标准
- [ ] 有一份"新代码导出"的完整体积/耗时/内存报告，落 `_体积分析/`；
- [ ] 明确 gzip 生效与否、PNG 来源，回填到本文档 §1。

## 4. R1 打开提速（收益最高）

### 现状证据
[boot.ts:76-78](../src/services/export/reader/client/boot.ts)：`method==='none'` 时走 `JSON.parse(decodeURIComponent(escape(atob(...))))` —— `escape`/`decodeURIComponent` 是老式 UTF-8 解码，对 260MB 逐字符扫描，是**打开慢头号元凶**（仅 none 路径）。
[boot.ts:68-109](../src/services/export/reader/client/boot.ts)：无论哪条路径，都**全量** `JSON.parse` 27 篇后才 `window.app.init()`。

### 目标
- 首屏秒开：先渲染封面/目录，不等全量解析；
- 内存峰值从 GB 级降到几十 MB。

### 设计（两档，先渐进后彻底）

**R1-a 解码路径修复（低风险，先做）**
- 把 `decodeURIComponent(escape(atob(b64)))` 换成 `TextDecoder`：
  `JSON.parse(new TextDecoder().decode(Uint8Array.from(atob(b64), c => c.charCodeAt(0))))`
- 或更优：`atob` 后分块填 `Uint8Array`，避免一次性超长串。
- 仅影响 `none` 兜底路径，不改数据格式；gzip 路径（Worker）本就高效，保留。

**R1-b 首屏懒解析（根治）**
- *渐进档（改动小，先上）*：
  - 导出时把「封面 + 配置 + 全部文章的**元数据**（标题/分类/日期/坐标）」单独打成一个**小 base64 块**（KB 级）；
  - 正文/媒体留在第二块；boot 先解第一块 → 立即渲染目录与封面 → `requestIdleCallback` 后台解第二块填正文。
  - 媒体本身已有 `IntersectionObserver` 懒加载（[media.ts](../src/services/export/reader/client/media.ts)），保留。
- *彻底档（后做，收益最大）*：
  - 数据布局改为「索引块 + 每篇一个媒体块」，媒体二进制按篇拼接、索引记录偏移；
  - 滚动到哪篇才解哪篇媒体块；打开只读索引。

### 实施步骤
1. R1-a：改 [boot.ts](../src/services/export/reader/client/boot.ts) 三处解码（76-78、99-100 及降级处），统一 `TextDecoder`；保留 Worker/gzip 路径。
2. R1-b 渐进档：改 [reader.worker.ts](../src/services/export/reader.worker.ts) 拆"元数据块 + 正文块"，改 [reader.ts](../src/services/export/reader/reader.ts) / [readerSkeleton.ts](../src/services/export/reader/readerSkeleton.ts) 注入两个块，改 [boot.ts](../src/services/export/reader/client/boot.ts) 分阶段解码。
3. 回归：`npm run test`（含 `src/services/export/reader.test.ts`）、手测导出包首屏与滚动加载。

### 验收标准
- [ ] 首屏（封面+目录）**秒开**，不等正文/媒体解析；
- [ ] 内存峰值较基线**降一个量级**（Performance 记录）；
- [ ] 全文检索、媒体懒加载、翻页无回归；
- [ ] `TextDecoder` 路径对 `none` 与 `gzip` 两种产物都正确。

### 风险与回退
| 风险 | 缓解 |
|---|---|
| 分块注入改变模板锚点，旧模板加载失败 | 模板带版本锚点校验（[reader.ts](../src/services/export/reader/reader.ts) 已有 `校验模板` 逻辑），不匹配回退动态骨架 |
| 懒解析导致全文检索时数据未就绪 | 检索触发时 await 后台解码完成；或检索前主动全量解码 |
| `Uint8Array.from` 大串仍占内存 | 分块 `atob` + `set` 填充，避免中间超长串 |

## 5. R2 媒体格式归一（PNG→WebP，减硬体积）

### 现状证据
[fileHelpers.ts:72-76](../src/utils/fileHelpers.ts) `compressImage` **默认 `format='webp'`**、maxWidth 1200、quality 0.8 —— 上传链路已转 WebP。但阅读包含 **58.8MB PNG**，说明**某些 PNG 逃过了压缩**（可能来源：粘贴截图、视频封面、`coverImage/backImage`、`rawHtml` 内嵌、或 `compressImage` WebP 失败回退时保留原 PNG）。
PNG 是无损格式，照片类内容用 WebP/JPEG 可压到 **1/5~1/10**。这是 gzip 生效后**最大的减体积项**（gzip 救不了已压缩的 PNG，但能"避免它一开始就这么大"）。

### 目标
阅读包内照片类图片统一 WebP/JPEG，消灭异常 PNG 大户。

### 实施步骤
1. **审计**（依赖 R0）：定位 58MB PNG 的来源 —— 按 `mime + 字段 + 文章` 统计，列出 Top 大户。
2. **堵漏**：对导出链路所有图片出口统一过 `compressImage(..., 'webp')`：
   - 覆盖 `coverImage`/`backImage`、`blocks` 内 image/video 封面、`rawHtml` 内嵌图、粘贴截图；
   - `compressImage` 的 WebP→JPEG 回退（[fileHelpers.ts:138-156](../src/utils/fileHelpers.ts)）需保证**不保留原 PNG**。
3. **阈值**：>某尺寸（如 500KB）的 PNG 强制转 WebP；动图 GIF 保留（转 WebP 动画另议）。

### 验收标准
- [ ] 同等内容下 PNG 占比显著下降（目标：58MB → <10MB）；
- [ ] 图片视觉质量可接受（WebP quality 0.8 基线）；
- [ ] 封面/封底高清图仍清晰（封面走 2400px + 0.92，不误伤）。

### 风险与回退
| 风险 | 缓解 |
|---|---|
| 透明 PNG 转 WebP/JPEG 丢失透明通道 | 透明图用 WebP（支持 alpha），仅不透明图才可转 JPEG |
| 统一转码拖慢导出 | 转码在 [reader.worker.ts](../src/services/export/reader.worker.ts) Worker 内做，不卡主线程 |
| 封面高清度下降 | 封面/封底保留独立高质量档，不套通用阈值 |

## 6. R3 压缩/编码策略（去双重 base64 + gzip 兜底）

### 现状证据
双重 base64：媒体在 JSON 内已 base64（×1.33），整个 JSON 再 base64（×1.33）= 1.77×。
[reader.worker.ts:52](../src/services/export/reader.worker.ts) 对 JSON 做 gzip —— **gzip 能找回 base64 膨胀**，故 gzip 生效时双重编码的膨胀已被抵消大半；**none 时（历史产物）膨胀全保留**。
[boot.ts:76](../src/services/export/reader/client/boot.ts) `method` 缺失即取 `'none'`。

### 目标
- none 场景去掉双重 base64（省约 25%）；
- 确保导出**始终 gzip**，不静默落到 `none`（落 none 时给告警而非沉默）。

### 设计
- **gzip 兜底（先）**：`compressData`（[compression.ts](../src/services/export/compression.ts)）两层（CompressionStream→fflate）都失败才 none；导出完成时若 `compressionMethod==='none'`，**toast 告警**（生产构建 drop console，须用 toast 而非 console）。这是"确保走 gzip"的最小改动。
- **去双重 base64（后，仅当 R0 证实 none 仍是常态/收益可观）**：媒体二进制单独拼块、仅 base64 一次；元数据单独 gzip+base64；阅读器按偏移索引切媒体。此改动与 R1-b"彻底档"数据布局**合并设计**（同一套索引+分块）。

### 验收标准
- [ ] 导出产物 `__SWS_COMPRESSION_METHOD__` 恒为 `gzip`；落 `none` 时有可见告警；
- [ ] none 场景（若仍存在）体积较基线降约 25%；
- [ ] 新旧格式都能被阅读器解析（带格式版本号）。

### 风险与回退
| 风险 | 缓解 |
|---|---|
| 去双重 base64 改数据布局，与旧阅读器不兼容 | 数据段带 `formatVersion`，阅读器按版本分支解析；旧包仍可开 |
| gzip 对已压缩媒体无益，收益不及预期 | 与 R2 协同：先减 PNG 再谈编码；R3 收益以 R0 实测为准，不预设 |

## 7. R4 视频降质/降码率（需用户决策）

### 现状证据
视频 mp4 **80.8MB（占硬体积 55%）**，两篇视频文章占 96MB。单文件约束下视频必须内嵌。

### 待决策项（开发前需确认）
1. **是否允许降分辨率/码率**？（工法视频是否需要 1080p，720p 是否足够）—— 允许则 80MB 可再压一半以上；
2. 或保持原视频，仅靠 R1-b"视频懒解码"避免拖慢打开（不减体积、只提速）。

### 设计（若允许降质）
- 导出时对视频转码/降采样（浏览器端 `MediaRecorder` 或后端 ffmpeg —— 项目已有 `ffmpeg` 相关目录，可评估复用）；
- 或提供导出选项："高清（大包）/ 标清（小包）"。

### 验收标准
- [ ] 视频观感满足工法展示需求；
- [ ] 包体积按决策档位下降（标清目标：80MB → <40MB）。

## 8. R-ENV OneDrive 存放策略（零代码，即时）

阅读包在 OneDrive 目录下。若开启**按需文件**，双击打开 260MB 会先从云端下载 —— 这是代码之外的打开慢主因。

**建议**：阅读包设为「始终保留在此设备」，或移出同步目录再分发。**零改动、立刻见效**，与 R1 互补。

## 9. 落地顺序与收益汇总

| 顺序 | 动作 | 体积 | 打开速度 | 内存 | 风险 |
|---|---|---|---|---|---|
| 0 | **R0 基线验证** | — | — | — | 无（先测后改） |
| 1 | R-ENV OneDrive | — | ✅✅ | — | 无 |
| 2 | R1-a 解码修复 | — | ✅✅ | ✅ | 低 |
| 3 | R1-b 懒解析 | — | ✅✅✅ | ✅✅✅ | 中 |
| 4 | R2 PNG→WebP | ✅✅✅ | ✅ | ✅ | 中 |
| 5 | R3 gzip 兜底/去双重 | ✅~✅✅ | ✅ | ✅ | 中 |
| 6 | R4 视频降质 | ✅✅ | ✅ | ✅ | 需决策 |

**组合预期**（在 R0 校准后修正）：
- gzip 生效前提下：体积 **~150MB → <60MB**（主要靠 R2 砍 PNG + R4 砍视频），首屏秒开；
- 若历史产物为 none：R3 去双重 + R2 可从 259MB → 约 50MB。

**两个待用户拍板的决策点**：
1. **视频是否允许降分辨率/码率**（R4，决定最大头 80MB 能否再砍一半）；
2. **PNG 全局转 WebP 是否接受画质折衷**（R2，透明图用 WebP 保 alpha）。
