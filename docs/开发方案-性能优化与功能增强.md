**实施中发现的两处计划外风险（已修）**

1. **DOMPurify 会剥掉自定义 scheme**：实测默认配置把 `<img src="sws-media://…">` 的 src 静默删除 → 正文行内图片在阅读态会消失。修复：`sanitizeHtml` 的 `ALLOWED_URI_REGEXP` 取"DOMPurify 默认口径 + `sws-media`"，相对路径/锚点、`data:` 图片、`javascript:` 拦截三项行为均有测试锁定。
2. **引用不能直接当 src**：`BlockRenderer` 原有"data URL 先解码再当 src"分支不覆盖引用，会让 `<img>` 真的去请求 `sws-media://…`。修复：抽出 `needsDeferredSrc()` 统一处理（图片/视频/音频三处）。

## P0-A 媒体资产拆表（存储层重构）

### 现状证据

- `services/db.ts`：单库 `SWS_DATABASE_REACT`（version 3）单表 `journal_store`，**无任何索引**；`getArticles()`（L216）全表 cursor 扫描，启动时所有文章（含全部 base64）一次性进内存。
- 图片以 data URL 存在于 `Article.content`（HTML 字符串内）；保存时 `htmlToBlocks()` 解析出的 `blocks` 里 `ImageBlock.src`/`VideoBlock.src` 等**又完整存一份**（`src/types/blocks.ts` L32-56）——同张图落盘两遍。
- `useJournal.updateArticle`（L124）浅合并后整篇对象（含全部 base64）重写；`reorderArticles` 注释已明示"避免全表重写大 base64"是既有痛点。
- 量化参考：一张 1200px WebP ≈ 100~300KB，base64 后 ≈ 133~400KB；一篇 10 图文章 ≈ 2~4MB，双存储再翻倍。20 篇图文刊 ≈ 80MB+ 全量驻留内存。

### 目标

1. 媒体（图片/视频/音频/PDF）只存**一份**，独立于文章正文；
2. 启动只加载文章文本骨架，媒体按需解码；
3. 修改标题/分类/排序等元数据不再触碰媒体数据；
4. 旧数据平滑迁移，导出/导入链路行为不变。

### 设计

**存储结构（DB version 3 → 4）**

```
journal_store (不变)     key: article-{id} / config-{key}
    Article.content 中媒体位置改为引用：<img src="sws-media://{hash}">
    Article.blocks 中 src 同样为 sws-media://{hash}
media_store (新增)       key: {hash}（内容 SHA-1/SHA-256 前 16 位）
    value: { dataUrl: string, mime: string, size: number,
             refCount: number, createdAt: number }
```

- `hash` 取 data URL 的 base64 载荷哈希（复用 `services/graphCache.ts` 已有的 `contentHash()` 思路，或直接 `crypto.subtle.digest`），同图天然去重——多篇文章引用同一 logo/示意图只存一份。
- **引用协议**：`sws-media://{hash}` 是约定 URI，凡渲染/导出路径遇到它都走解析器还原。新增 `src/utils/mediaRefs.ts`：
  - `extractMediaRefs(html, blocks)` — 扫出全部 data URL，写 `media_store`，返回替换引用后的 html/blocks
  - `resolveMediaRefs(html, blocks)` — 引用 → data URL 还原（导出用）
  - `resolveToBlobUrl(src)` — 引用 → blob URL（渲染用，接入 `useBlobManager` 现有 Worker 解码链路）
  - `gcMedia(oldRefs, newRefs)` — 引用差集递减 refCount，归零删除

**写路径**（`useJournal.debouncedSaveArticle` / `saveArticle` 内改造）：

```
保存 → extractMediaRefs（新媒体入库 + refCount 累加）
     → 文章文本落盘（体积骤减）
     → gcMedia（被删掉的图引用递减）
```

**读路径**（渲染侧）：`useBlobManager.getBlobUrlAsync` 增加 `sws-media://` 分支——查 `media_store` 取 dataUrl → 走现有 Worker 解码 → blob URL（现有 LRU 缓存 300 条全部复用）。`BlockRenderer`/`ContentRenderer` 零改动（它们只认 `getBlobUrlAsync`）。

**导出路径**：`src/services/export/reader.ts`、`print.ts`、`utils/media.ts` 在组装前调 `resolveMediaRefs()` 把引用还原成 data URL——**导出产物格式完全不变**，离线阅读器仍是单 HTML 自包含。`useImportManager` 导入旧项目文件时：含 data URL 的老格式走 `extractMediaRefs` 一次性入库；含 `sws-media://` 的新格式直接落盘。

**迁移（懒迁移，首次启动执行）**：

1. `config-mediaMigrated` 标记不存在时触发；
2. 遍历 `journal_store` 的 `article-*`，检测 `content`/`blocks` 中含 `data:` 的条目，逐篇 `extractMediaRefs` + 回写（每 5 篇让出主线程，顶部进度条复用 `importProgress` 通道）；
3. 全部完成后写标记。**迁移期间不删除原数据字段**（见风险回退）。

**GC**：删除文章 → 其引用全量递减；替换图片 → 新旧差集递减。`db-inspect` skill 相应增加"媒体引用孤儿检查"。

### 实施步骤

1. `src/utils/mediaRefs.ts` + 单测（提取/还原/GC 幂等性）；
2. `db.ts`：version 4、`media_store` 建表、`saveMedia/getMedia/decMediaRefs` 接口；
3. `useJournal.ts` 保存链路接入 extract + gc；启动迁移流程；
4. `useBlobManager.ts` 增加 `sws-media://` 解析分支；
5. 导出三处（reader/print/utils/media）接入 `resolveMediaRefs`；
6. `useImportManager` 新旧格式兼容；
7. 端到端验证 + `db-inspect` 更新。

### 验收标准

- 迁移后 `media_store` 条目数 = 去重后媒体数；`journal_store` 单条体积下降 ≥50%（图文篇）；
- 启动加载（20 篇图文测试刊）内存占用显著下降，`useMemoryMonitor` 峰值对比记录在案；
- 修改标题/排序不再产生媒体写入（db 性能指标 `saveTime` 对比）；
- 导出 reader/print 与改造前逐篇对比无差异（含图片显示）；
- 旧项目文件导入正常；迁移中断（关页）后重启可续。

### 风险与回退

| 风险 | 缓解 |
|------|------|
| 迁移中断导致部分文章已改引用、媒体未入库 | 先写 media_store 再改文章（顺序保证）；迁移可续跑 |
| refCount 不准导致媒体被误删 | **迁移首版不物理删除**，GC 只对新写入生效；一个版本周期后确认无孤儿再启用删除 |
| 导出路径漏改一处导致离线阅读器缺图 | 导出前统一入口收口（`export/index.ts` 门面层做 resolve）；E2E 对比测试 |
| blocks 与 content 引用不同步 | extract/replace 同一函数内成对处理，单测覆盖双存储一致性 |

## P0-B 保存链路 flush（正确性修复）

### 现状证据

保存的真实链路存在**两层异步窗口**：

```
Ctrl+S / 保存按钮
  → useEditorState.handleSave（L93）：requestIdleCallback(doSave, {timeout:500})  ← 窗口① ≤500ms
    → App.handleSaveArticle → useJournal.updateArticle
      → debouncedSaveArticle（L106）：setTimeout 1000ms                            ← 窗口② =1000ms
        → db.saveArticle
```

用户点了"保存"、看到"已自动保存"（`useEditorKeyboard.ts` L32），实际 1.5 秒内关页/崩溃则**静默丢数据**。项目无任何 `beforeunload`/`pagehide`/`visibilitychange` flush 逻辑（全库检索无命中）。

### 目标

点下保存后**最迟在离开页面前必然落盘**；后台防抖保存同样不丢。

### 设计

1. **`useJournal` 暴露 `flushPendingSaves(): Promise<void>`**：清空 `saveTimersRef` 中全部定时器，立即执行对应保存并 await 全部完成。
2. **页面生命周期挂钩**（`useJournal` 或 `App` 根部）：
   - `visibilitychange → hidden`：调用 `flushPendingSaves()`（移动端/切标签页场景，比 pagehide 更早）；
   - `pagehide`：兜底再调一次（幂等）；
   - 说明：IndexedDB 事务在页面卸载时会继续提交，`pagehide` 中同步发起 `put` 是可靠的；不使用 `beforeunload` 阻塞弹窗（打扰用户，且现代浏览器对其限制越来越多）。
3. **压缩窗口①**：`handleSave` 的 doSave 拆两段——**落盘立即执行**（不等 idle），`htmlToBlocks` 解析保留在 idle 回调里**补写** blocks 字段（blocks 是渲染缓存，缺失时打开会现算，不影响数据完整性）。即：文本永不延迟，缓存可延迟。
4. **防抖加 maxWait**：`debouncedSaveArticle` 除 1000ms 防抖外加 3000ms 上限（持续输入场景最多 3 秒必落一次盘），实现用"记录首次入队时间，超 maxWait 则不重置计时器"。

### 实施步骤

1. `useJournal.ts`：`flushPendingSaves` + `pagehide`/`visibilitychange` 挂钩 + maxWait；
2. `useEditorState.ts`：`handleSave` 拆分"立即落盘 / idle 补 blocks"；
3. 测试：`src/__tests__/useJournal.test.tsx` 增加「防抖窗口内 flush 落盘」「pagehide 触发 flush」「maxWait 生效」用例（fake timers）。

### 验收标准

- 模拟"点保存后立即 pagehide"，`db.saveArticle` 必被调用（测试断言）；

## P1-A 回收站 + 自动备份（数据安全）

### 现状证据

- 删除文章仅 `window.confirm` 一道闸（`useJournal.deleteArticle` L189），确认即物理删除 `db.deleteArticle`，**无恢复途径**；
- 数据存浏览器 IndexedDB，**不在 OneDrive 同步范围**（OneDrive 只同步代码）：清浏览器数据 / 换机器 = 全部丢失；
- 现有 `useImportManager`（项目 JSON 导入）+ `useExportManager`（导出）已具备备份闭环的手动版。

### 目标

误删可恢复；数据有自动异地副本（本地文件夹）。

### 设计

**A. 回收站（软删除）**

- `Article` 增加 `deletedAt?: number`；`deleteArticle` 改为写标记（不再物理删）；
- `sortArticlesByPriority` / 各渲染列表默认过滤 `deletedAt` 存在的条目；
- Sidebar 底部加「回收站」入口（或分类列表内一项）：列出已删文章（标题 + 删除时间），操作 = 恢复 / 彻底删除（`window.confirm`）；
- 自动清理：`deletedAt` 超 **30 天**的在启动时物理清除（提示条告知清理了几篇）；
- 封面/封底不可删规则不变。

**B. 自动备份（File System Access API）**

- 用户在设置/工具菜单授权一个备份文件夹（`showDirectoryPicker()`，句柄存 IndexedDB `config-backupDir`，`queryPermission/requestPermission` 处理续期）；
- 触发时机：① 手动"立即备份"；② 每次文章落盘后防抖 5 分钟自动备份；③ 关页前有未备份更改则补一次（接 P0-B 的 flush 通道）；
- 产物：`SWS备份-YYYYMMDD-HHmm.json`（复用现有导出 JSON 格式），保留**最近 10 份**滚动删除；
- 不支持该 API 的浏览器（Firefox/Safari）：降级为"提醒手动导出"（toast + 打开导出弹窗），不假装成功。

### 实施步骤

1. `src/types/models.ts` 加 `deletedAt`；`useJournal` 软删除 + 恢复 + 彻底删除 + 启动清理；
2. 过滤逻辑收口到 `src/utils/articleFilter.ts`（已有该模块）；
3. UI：Sidebar 回收站入口 + 列表面板（可复用 CategoryManagerModal 的弹窗模式）；
4. `src/services/backup.ts`：目录授权、写文件、滚动清理、降级判断；
5. 设置入口 + 状态提示（已授权目录名、上次备份时间）；
6. 测试：软删/恢复/30 天清理逻辑单测；backup 降级路径单测。

### 验收标准

- 删除 → 回收站可见 → 恢复后内容/排序完好；
- 30 天前的已删文章启动时被清除；
- 授权后落盘改动 5 分钟内自动生成备份文件，10 份滚动；
- 未授权/不支持浏览器不报错、给出明确提示。

### 风险

| 风险 | 缓解 |
|------|------|
| 目录句柄权限过期（Chrome 会回收） | 每次备份前 `queryPermission`，未授权则提示重新授权，不静默失败 |

## P2-A 撤销/重做可靠化

### 现状证据

- `FormattingToolbar.tsx` L77 undo/redo 走 `document.execCommand('undo')`——仅覆盖 contenteditable 内部栈；
- 跨 React 状态的操作（AI 插入摘要 `useEditorCommands.handleAiSummary`、标题修改、图片替换 `useImageToolbar`、字体/行高设置）**不在栈内**：Ctrl+Z 会"撤销不动"或撤销错对象；
- `execCommand` 已被标记 deprecated，行为跨浏览器不一致。

### 目标

Ctrl+Z / Ctrl+Y 对**所有编辑操作**（打字、AI 改写、图片替换、标题修改）行为一致可预期。

### 设计

轻量快照栈（不引第三方库）：

- `useEditorState` 内建 `undoStack`/`redoStack`，条目 = `{ content, title, formData 摘要 }` 的快照；
- 压栈时机：① 打字输入防抖 500ms 压一次（合并连续输入）；② AI/图片/结构化操作**前**立即压一次（before-hook）；
- **容量约束**：快照按总字节上限 5MB LRU 淘汰（大 HTML 快照 ×30 会吃内存，用 `content.length` 估算）；
- Ctrl+Z：当前状态入 redoStack → 弹栈恢复（content 写回 `contentRef.innerHTML`，title/formData 走 setState）；
- **切换文章清空栈**（跨文章撤销无意义）；
- 打字期间不再依赖 `execCommand('undo')`——统一走快照栈（体验差异：撤销粒度从"逐字符"变为"逐 500ms 段"，可接受且更符合编辑器惯例）；`execCommand` 只保留 formatBlock/bold 等格式命令。

### 实施步骤

1. `components/editor/hooks/useUndoStack.ts` 新 hook（快照/恢复/容量）；
2. `useEditorState.handleSave`、`useEditorCommands`（AI 操作）、`useImageToolbar`（图片替换）接入 before-hook；
3. `useEditorKeyboard` 的 Ctrl+Z/Y 改走快照栈；
4. 测试：压栈节流、容量淘汰、跨操作恢复正确性。

### 验收标准

- 打字 → AI 插入摘要 → Ctrl+Z 两次，逐级回到操作前状态；
- 图片替换后 Ctrl+Z 恢复原图；
- 栈内存占用受控（5MB 上限生效，超过时最旧快照被淘汰）；
- 切换文章后 Ctrl+Z 不回溯到上一篇。

## P2-B 图谱代码注入架构改造（?raw 内联）

### 现状证据

- `src/utils/graph/graphEngine.ts`（35KB）与 `Renderer.ts`（15KB）导出 `generateGraphEngineCode()/generateRendererCode()`，**实际 JS 源码嵌在模板字面量里**（AGENTS.md 明示"模板内严禁反引号/${}"）；
- `scripts/post-build.js` L13-34 靠**反引号计数基线**（graphEngine=4 / Renderer=2）防模板提前闭合——这是"运行期爆炸"降级为"构建期报错"的补丁，治标；
- 模板内代码**过不了 typecheck**，写错只能等 iframe 运行时发现；约 50KB 代码无法用编辑器的跳转/补全/格式化。

### 目标

图谱运行时代码成为**普通源文件**：语法错误构建期即报、可类型检查、可自由使用模板字符串；注入机制不变（仍是 srcdoc 内运行）。

### 设计

- 把模板内的 JS 抽出为独立文件 `src/utils/graph/runtime/engine.ts` + `runtime/renderer.ts`（**纯 ES2017 脚本**，不 import/export——它最终拼进 srcdoc 的 `<script>`，模块语法会破坏运行）；
- 用 Vite 的 `?raw` 导入：`import engineCode from './runtime/engine.ts?raw'`——构建期把文件**原文**内嵌为字符串，零运行时成本；
- `generateGraphEngineCode()` 退化为 `engineCode + rendererCode` 的薄拼接层；若模板内有变量插值需求，改为**占位符 + 运行时 replace**（如 `__SWS_D3_SRC__`，现有代码已有此模式）；
- `post-build.js` 反引号基线校验**退役**，替换为更简单的守卫：构建时 `new Function(engineCode)` 语法冒烟（能编译即通过）；
- typecheck 注意：runtime 文件会被 tsc 检查（这是收益），需用 `/// <reference` 或全局声明覆盖其用到的 window 自定义字段（`src/global.d.ts` 已集中管理）；
- **行为零变化**：生成的 srcdoc 字符串应与旧版逐字节一致（保留一个对比测试：新旧代码字符串 normalize 后比对）。

### 实施步骤

1. 抽取 runtime 两文件（机械搬移，不改逻辑）；
2. `?raw` 导入 + 拼接层改写；变量插值改占位符；
3. `post-build.js` 守卫替换（反引号计数 → `new Function` 冒烟）；
4. 对比测试：新旧生成 srcdoc 一致；图谱功能手测（交互/搜索/打印 SVG）；
5. `graphRenderer.ts`、`graphQuality` 相关测试跑全。

### 验收标准

- typecheck 覆盖图谱运行时代码（故意写错一处语法，构建/类型检查即报）；
- 图谱交互、关键字搜索、打印 SVG 与改造前一致；
- `post-build.js` 新守卫通过；产物体积无显著变化。

### 风险

- runtime 文件里若有对模板拼接变量的隐式依赖，抽取时会遗漏——抽取后逐段 grep `\$\{` 与字符串拼接点核对；
- `?raw` 依赖 Vite（测试环境 vitest 同样支持 `?raw`，需在 vitest 配置确认无碍）。
